# SECURITY.md

> Репозиторий проекта: https://github.com/TR-Artem/medical_booking

Документ описывает меры безопасности проекта «Онлайн-запись в медицинский центр».

## Секреты

- Настоящие значения хранятся только в `.env` и `.env.production`, оба файла в `.gitignore`.
- В репозитории есть только шаблоны: `.env.example` и `.env.production.example` с заглушками `change_me`.
- При компрометации: заменить `SECRET_KEY` и пароли БД, перезапустить сервисы, отозвать ключи SMTP.

## Версии зависимостей

- Runtime-зависимости закреплены в `requirements.txt`, инструменты разработки — в `requirements-dev.txt`.
- Неиспользуемые DRF, SimpleJWT, SendGrid и CORS удалены из зависимостей.
- Проверка уязвимостей: `make deps-check` (pip-audit), в CI — на каждый push.

## Доступ и роли

Роли: пациент, врач, администратор клиники, системный администратор.

- Панели администратора доступны ролям `admin` и `sysadmin`.
- Суперпользователь Django admin — только `sysadmin`; администратор клиники
  не имеет полного доступа к Django admin.
- Пациент не может открыть чужую запись: отмена чужой записи возвращает 404.
- Закрытые разделы без входа перенаправляют на страницу входа, при недостатке прав — 403.
- Вход ограничен: 5 неудачных попыток на логин+IP и 20 на IP за 15 минут
  (Redis-кэш). При недоступном Redis лимит отключается, чтобы не блокировать вход.

## Пароли и вход

- Вход по username или e-mail без учёта регистра.
- Сброс пароля — одноразовая ссылка Django, срок действия 1 час.
- Смена пароля доступна в профиле.
- Пароли демо-учёток публичны и только для стенда; `seed_demo` сбрасывает их при каждом запуске.

## Конфигурация

- `DEBUG=False` в production; трассировки не отдаются.
- `ALLOWED_HOSTS=localhost,127.0.0.1`; для домена задаётся явно.
- Заголовки: `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: same-origin`.
- Cookies: `HttpOnly` для сессии и CSRF; на HTTPS включаются `Secure`-флаги.
- Контейнеры приложения работают от пользователя `app` (uid 100), не от root.
- SMTP имеет таймаут 10 секунд; письма отправляются Celery-задачей с повторами.
- Логи Docker ограничены по размеру, `/healthz/` не раскрывает внутренние детали.

## Персональные данные

- При регистрации требуется согласие на обработку ПДн (ФЗ-152).
- Опубликована страница `/privacy/` с политикой и текстом согласия.
- Для реальной клиники нужны: уведомление Роскомнадзора, приказ о назначении
  ответственного, сроки хранения и процедура удаления данных.

## Данные и восстановление

- Бэкап: `make backup` / `deploy/backup.sh` — `pg_dump` gzip + ротация 14 дней.
- На VPS бэкап запускается по cron ежедневно в 03:15.
- Восстановление: `make restore BACKUP=backups/<файл>.sql.gz` в отдельную БД.
- Каталог `backups/` и файлы `*.sql`, `*.dump`, `*.gz` исключены из git.

## Инфраструктура

- `deploy/setup-vps.sh` включает UFW (22/80/443), fail2ban и unattended-upgrades.
- HTTPS: Let's Encrypt, HTTP→HTTPS, HSTS; `SECURE_PROXY_SSL_HEADER` настроен.
- Health-check `/healthz/` пригоден для внешнего uptime-мониторинга.

## Ограничения

- Нет капчи и аудита действий пользователей в отдельной таблице: события пишутся в логи.
- Нет WAF и защиты от распределённого перебора beyond rate limit.
- Локальный демо-стенд работает по HTTP; HTTPS включается на VPS.
